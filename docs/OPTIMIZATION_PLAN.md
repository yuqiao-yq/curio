## 开发与验证

- 锁文件未改动；建议 `nvm use` 使用 `.nvmrc` 中的 Node 22.22.2。兼容 Node 20.19+ 或 22.12+；CI 的 Node 20 应使用最新小版本。
- 最终验证：`pnpm compile` 和 `pnpm lint` 通过；`pnpm test:ci` 共 18 个测试文件、198 项测试通过；`pnpm bench` 完成；Chrome MV3 和 Firefox MV2 构建通过。构建后检查确认：默认包不含 OAuth/identity 配置，history 和网站访问均声明为可选权限。
- 浏览器真实双设备同步、权限交互、首屏与拖拽性能不能以单元测试代替。
- 不在仓库提交密钥、真实书签或浏览历史。Google Drive 客户端 ID 是公开配置，不应提供客户端密钥。

## 已知边界与下一步

1. 当前 `storage.sync` 在首次启用时会按实体时间合并，日常同步仍按整包传输。已看到远端新版本且本地有未推送修改时暂停自动覆盖；远端可能延迟到达，并发设备编辑仍可能覆盖。下一步需要实体修订、删除标记与逐条操作队列。
2. 同步 API 写入成功不等于所有远端设备已收到数据；书签待同步标记随数据持久保存，关闭页面不会清掉；下次启动或在线事件会重新尝试。定时重试仍依赖页面存活，没有后台持续上传。偏好尚未使用独立的持久待同步版本。
3. 本地写锁覆盖当前扩展上下文；不同浏览器之间不共享锁。不支持 Web Locks 的浏览器会明确拒绝写入，需升级浏览器。
4. 本地备份只保留最近 10 次操作前的库和偏好，不备份 AI 配置、正文、向量或对话；应定期另存 JSON。跨页面刷新暂只更新书签和分类，避免覆盖另一页面尚未保存的偏好修改。
5. Google Drive 下一步先落实冲突协议，再完成 Chrome 授权与 appdata 读写。Firefox 需要独立验证授权码、PKCE 与回调方案，不能直接复用 Chrome 扩展客户端。
6. 后续补充真实浏览器的双页面操作、离线和权限验收，再以测量结果决定是否拆分状态订阅、分页读取正文或增加段落向量。
